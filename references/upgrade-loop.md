# 技能库升级循环：入库过闸，检索过闸

## 为什么要过闸

技能库的思路来自 Voyager（NVIDIA，arXiv 2305.16291）：agent 把验证过成功的代码封装成可复用技能，不断增长，能力随之提升。

但后续研究发现一个反直觉的坑（arXiv 2512.17102，Reinforcement Learning for Self-Improving Agent with Skill Library）：

> 技能库带来的收益会被"技能利用能力不足"抵消——不恰当的应用直接导致任务失败。

也就是说，**技能库越大，误用风险越高**。所以关键不是"多存"，而是"存得准 + 找得准"。

## 入库流程

```
一个做法被用过 2 次且都成功
├─ 写正文 skills/<name>.md
│    1. 名字（动词开头，如 "分片下载并逐片校验"）
│    2. 前提（什么环境下成立：网络状况、文件大小、工具版本）
│    3. 步骤（可照抄的命令/序列）
│    4. 验证（怎么确认这次真的生效了，不是"看起来对"）
│    5. 边界（什么情况下不能用，反例是什么）
│    6. 失败史（如果用过但失败过，写清失败条件）
└─ 索引加一行：`- <名字> | 前提：… | 验证：… | 边界：…`
```

**为什么是 2 次**：一次成功可能是运气、是环境恰好配合。2 次成功才配叫"可复用"。

## 检索流程（比入库更重要）

### 第一步：三维打分排序

候选条目用三个维度打分（借鉴 Generative Agents 的记忆检索，Park et al. 2023）：

| 维度 | 权重 | 怎么打分 |
|---|---|---|
| **相关性 relevance** | 0.5 | 前提逐项对上 = 1.0；对上一半 = 0.5；基本对不上 = 0 |
| **重要性 importance** | 0.3 | 成功次数 ≥5 → 1.0；3–4 → 0.7；1–2 → 0.4；从未成功 → 0 |
| **时效性 recency** | 0.2 | 30 天内用过 → 1.0；3 个月内 → 0.6；更久 → 0.3 |

`score = 0.5*relevance + 0.3*importance + 0.2*recency`

按分数降序取前 3 条展开正文。**只看前 3 条**——第 4 条开始噪声大于价值。

### 第二步：执行与记录

```
3. 对得分最高的条目，逐项核对前提：环境一样吗？工具版本一样吗？数据规模一样吗？
4. 全部对上才展开正文照做；有一项对不上就降权，看下一条
5. 用完后回写条目元数据：
   ├─ 成功 → 成功次数 +1，更新"最近使用"
   └─ 失败 → 在"失败史"记原因（前提不符/执行出错/环境变化）
```

### 第三步：低分条目的清理

- 30 天内 relevance 从未 >0.5 → 说明前提写得太窄或太宽，重写
- 连续 3 次因前提不匹配失败 → 前提描述失真，重写或删除
- 条目间前提高度重叠 → 合并

## 反模式

| 反模式 | 后果 |
|---|---|
| 一次成功就入库 | 库被偶发成功污染 |
| 只存步骤不存前提 | 下次环境不同直接照抄，失败 |
| 只存结果不存验证方法 | 无法确认是否真的生效 |
| 索引写得太长 | 索引本身变成负担，回到"全量加载"老路 |
| 从不删除 | 库膨胀，检索成本超过收益 |
| 前提不匹配仍硬套 | 这是技能库反噬的主要形式 |

## 与其他机制的关系

- **失败** → 写进 `memory/anti-patterns.md`（不是技能库）
- **成功且可复用** → 进 `skills/`
- 两者都是"经验"，但一个是"不要做什么"，一个是"可以怎么做"，分开放，避免混淆

## 自检问句（每次打算用技能库时问自己）

1. 我是在找一个**已验证的做法**，还是在找一个**安慰**？
2. 这条的前提，我逐项对上了几个？
3. 如果它失败了，我能立刻知道是前提不对还是执行不对吗？
