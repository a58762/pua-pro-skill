# 恢复与检查点

## 要解决什么问题

长任务最常见的失败不是做错，而是**中断后丢失状态**：会话被压缩、沙箱被重置、工具被降级。恢复时若不知道"已经验证过什么、排除了什么"，就会从头再试一遍死路。

主流工程实践的共同结论：
- 压缩时要保住的不只是任务描述，还有**工作区、会话与验证工具**（Agentastic 的 compaction recovery 指南）
- 记忆做成版本化文件系统，才能跨会话恢复并迁移推理（Git Context Controller）
- 24/7 长期 agent 最难的问题不是执行，而是**会话之间的一致性**

## 检查点格式（紧凑，够用）

```
[PUA-CHECKPOINT]
目标：<一句话>
验收：<可测判据>
已验证：<做成了什么，附证据位置>
已排除：<试过且失败的路 + 失败原因>
失败数/等级：n → Lx
下一动作：<下一步具体做什么>
更新于：<时间>
```

**写在哪**：`/sandbox/workspace/.pua/journal.md`（持久层，覆盖写，不追加）。

**什么时候写**：
1. 一个子目标完成、要转向下一段时
2. 明显感觉上下文快满时（宁可多写）
3. 交给用户等待回复前
4. 长任务每 30 分钟一次

## 恢复规则

```
读 journal.md
├─ mtime > 2h → 忽略（陈旧状态会污染判断，宁可重来）
├─ mtime < 2h → [Calibration]
│    1. 核对「目标」是否仍是当前任务 → 不是就忽略
│    2. 读「已验证」→ 不重复劳动
│    3. 读「已排除」→ 不许再走这些路
│    4. 接上「失败数/等级」→ 压力不因中断重置
│    5. 从「下一动作」继续
└─ 不存在 → 正常冷启动
```

**关键约束**：检查点只在**同一任务**内继承。换了任务，必须作废重写——否则会把上一条任务的失败计数接过来，压力等级从一开始就偏高，行为会变形。

## 沙箱重置后的最小恢复

```
1. mkdir -p /sandbox/workspace/.pua/{system,memory,skills}
2. 读 .pua/system/always.md（若丢失，按 SKILL.md 第 1 节重建）
3. 读 memory/evolution.md 与 anti-patterns.md
4. 读 skills/index.md
5. 读 journal.md，按上面的规则判断是否恢复
```

工作区文件在持久层，重置不会丢；但 `/opt`、`/usr/local/bin`、`/root` 会清——工具链需重建时不在此技能职责内，只负责**任务状态**不丢。

## 反例

| 做法 | 为什么错 |
|---|---|
| 把检查点写成完整对话记录 | 太长，恢复时反而读不进去 |
| 检查点里写"基本完成了" | 无验收判据，恢复后无法判断 |
| 跨任务继承检查点 | 失败计数污染，压力等级失真 |
| 只在任务结束时写检查点 | 中断时什么都留不下 |
| 相信"我记得刚才试过了" | 压缩后这句话不再是事实 |
